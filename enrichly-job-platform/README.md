# Enrichly Job Automation Platform

A web application for creating and running automated jobs - HTTP calls that run on a repeating
interval or on demand, with execution history, retries, and failure visibility.

Built for the Enrichly Full Stack Developer Intern assignment. See [`ENGINEERING.md`](./ENGINEERING.md)
for architecture, the concurrency/retry design, product decisions, and known limitations.

**Stack:** Angular (TypeScript) · ASP.NET Core (.NET 8 / C#) · MySQL 8 · Docker

## A note on how this repository was produced

This project was generated by Claude without a local .NET SDK, Node/npm registry access, or a
database to run migrations/tests against. That means:

- The code has **not** been compiled or executed by the author. It's been written carefully and
  reviewed line-by-line, and the backend has real xUnit tests (see `backend/src/JobPlatform.Tests`),
  but you should expect to fix small build errors on first run, the way you would with any code
  you haven't personally compiled yet.
- The EF Core migration is **generated automatically the first time you build the API Docker
  image** (see the `Dockerfile` and "Database migrations" below) rather than being hand-written
  and committed, since producing one correctly requires the real `dotnet-ef` tool.
- If something doesn't build, the most likely culprits are a NuGet/npm package version bump or a
  typo - both are quick to fix with the compiler error in hand.

## Quick start (Docker - recommended)

Requires Docker and Docker Compose.

```bash
cp .env.example .env
# edit .env - at minimum set a real JWT_SECRET (openssl rand -base64 48)

docker compose up --build
```

Then open:
- Frontend: http://localhost:4200
- API: http://localhost:5000 (Swagger UI at `/swagger` in Development mode)
- MySQL: localhost:3306

First run will take a few minutes (Angular npm install + .NET restore + migration generation).
The API waits for MySQL to report healthy and retries its own migration step for up to ~30s in
case MySQL is still initializing.

To see multiple workers safely sharing one queue (see `ENGINEERING.md`):

```bash
docker compose up --build --scale api=3
docker compose logs -f api
```
(Note: with more than one `api` replica only one gets the published `5000` port; scaling is
meant to be observed through the logs, not by load-balancing the frontend across replicas.)

## Local development (without Docker)

### Prerequisites
- .NET 8 SDK
- Node.js 20+ and npm
- MySQL 8 running locally (or via `docker compose up mysql`)

### Backend

```bash
cd backend
dotnet tool restore                       # installs the pinned dotnet-ef version
cd src/JobPlatform.Api

# create a database + user matching appsettings.Development.json, or edit the connection
# string there to match your local MySQL setup
mysql -u root -p -e "CREATE DATABASE enrichly; CREATE USER 'enrichly_app'@'%' IDENTIFIED BY 'devpassword'; GRANT ALL ON enrichly.* TO 'enrichly_app'@'%';"

# generate the migration (only needed once - it's created automatically inside Docker builds,
# but a local `dotnet run` outside Docker needs it generated locally too)
dotnet ef migrations add InitialCreate --output-dir Data/Migrations

dotnet run
```

The API applies pending migrations itself on startup - no separate `dotnet ef database update`
step is required once the migration exists.

Run tests:
```bash
cd backend
dotnet test
```

### Frontend

```bash
cd frontend
npm install
npm start
```

Opens on http://localhost:4200 and expects the API at http://localhost:5000 (see
`src/environments/environment.ts`).

## Environment variables

### Backend (`backend/src/JobPlatform.Api/appsettings.json`, or environment variables in
production using the `Section__Key` convention, e.g. `Jwt__Secret`)

| Variable | Description | Default |
|---|---|---|
| `ConnectionStrings__Default` | MySQL connection string | see `appsettings.json` |
| `Jwt__Secret` | HMAC signing key for JWTs. **Change this in any real deployment.** | placeholder |
| `Jwt__Issuer` / `Jwt__Audience` | JWT issuer/audience | `enrichly-job-platform` |
| `Jwt__ExpiryMinutes` | Access token lifetime | `120` |
| `Cors__AllowedOrigins__0` | Origin allowed to call the API from a browser | `http://localhost:4200` |
| `Worker__EnableScheduler` | Run the interval-job scheduler in this process | `true` |
| `Worker__EnableWorker` | Run the job worker (claims + executes) in this process | `true` |
| `Worker__EnableReaper` | Run the stale-execution reaper in this process | `true` |

The three `Worker__Enable*` flags exist so you could, if you wanted, run a "web-only" API
instance with all three set to `false` behind a load balancer, and separate "worker-only"
instances with routing disabled - the code doesn't care which process a hosted service runs in.
This build runs all three in every API instance for simplicity (see `ENGINEERING.md`).

### Frontend

| Variable | Where | Description |
|---|---|---|
| `apiBaseUrl` | `src/environments/environment.ts` | API URL for local `ng serve` |
| `API_BASE_URL` | Docker container env var | API URL injected into `env.js` at container start (see `docker-entrypoint.sh`) - this is the URL **your browser** calls, so it needs to be reachable from wherever you open the app |

### Docker Compose (`.env`, see `.env.example`)

| Variable | Description |
|---|---|
| `MYSQL_PASSWORD` / `MYSQL_ROOT_PASSWORD` | MySQL credentials |
| `JWT_SECRET` | Passed through to the API |
| `FRONTEND_ORIGIN` | CORS origin allowed to call the API |
| `API_BASE_URL` | Passed through to the frontend container |

## Using the app

1. Open the frontend and click "Create one" to register an account.
2. Click **+ New job**, give it a name, an HTTP method + URL to call (try
   `https://httpbin.org/status/500` to see failure/retry behavior, or `https://httpbin.org/get`
   for a job that always succeeds), and either "Manual only" or a repeating interval.
3. From the job detail page, click **Run now** to trigger it immediately, or wait for the
   scheduler if it's on an interval.
4. Watch the execution history update (the page polls every few seconds) - status moves
   Pending → Running → Succeeded/Failed, with output/error details and retry attempts visible.
5. A permanently-Failed execution has a **Retry** button; a still-Pending one has **Cancel**.
6. **All Executions** in the nav shows history across every job, filterable by job and status.

## Database migrations

Migrations live in `backend/src/JobPlatform.Api/Data/Migrations/`. If that folder is empty (as
shipped, for the reasons explained above), the API's Docker build step generates
`InitialCreate` automatically using the pinned `dotnet-ef` tool version in
`backend/.config/dotnet-tools.json`. For local (non-Docker) development, run the
`dotnet ef migrations add InitialCreate` command shown above once.

If you change the entity model later, generate a new migration the normal way:
```bash
cd backend/src/JobPlatform.Api
dotnet ef migrations add YourMigrationName --output-dir Data/Migrations
```
